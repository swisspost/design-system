<p className="lead">
  The KLP login widget shows the login link to anonymous visitors and the user menu to signed-in
  users of the Swiss Post customer login platform (KLP).
</p>

It is designed to be used in the `post-login` slot of the `post-header` component. The widget owns
the session: it asks the KLP platform who is signed in, keeps the session alive while the user is
active, and receives unread messages and sign-ins or sign-outs from other tabs as they happen. It
also renders the login link and every entry of the user menu, so your application only adds the
widget.

Once the user is signed in, a click on the avatar opens the user menu.

This user may switch account. Business users who may change company see the company switch
instead, and users who may do neither, such as private customers, see no switch at all. Use the
`Session` control above to see each of them.

## Environment

The `environment` property selects the KLP platform the widget talks to, and with it every URL the
widget calls: `prod` uses `n.account.post.ch`, the other environments use the matching test
platforms. Your page's origin has to be on that platform's allowlist, and the page has to be served
from a `post.ch` domain, so the session cookie is sent along.

If your page uses a Content Security Policy, allow the platform in `connect-src`, for both `https:`
and `wss:`, because the widget also opens a websocket to it.

## Service

The required `service` property names your application as it is registered with KLP. The widget
sends it as `app` and `service` with the login and the account and company switch, so KLP returns
the user to your application afterwards. If KLP knows your application under a different `app`
name, set the optional `app` property; `service` is still sent as is. Set `in-iframe` if your
application runs inside an iframe; KLP then keeps the switches and the logout inside it.

The account switch and the company switch are never shown together.

The texts come in German, French, Italian and English. The widget takes the first of these it
finds in the `language` property, `<html lang>` and the browser's preferred languages, and falls
back to German otherwise.

To replace a text, put an element with the matching `slot` into the widget. To replace a target,
set the URL property:

## Custom entries

To add entries of your own, put `post-menu-item`s into the widget without a `slot`. They are
listed between settings and logout, in the order you add them:

    <b>Always wrap custom entries in a `post-menu-item`</b>, with a link or a button inside. Only

## Before the session is known

Until the platform has answered, the widget shows an avatar without initials, so the header does
not shift once the session is known. If your page already knows the visitor's authentication state, set
`initial-state` accordingly (e.g. during SSR), so the widget renders in the correct state immediately.

## Unread messages

The Messages entry shows the number of unread messages the platform reports, and the avatar shows
a dot as long as there are any. Both update as messages arrive, without a reload. Use the
`Unread messages` control of the first example to see them.

### How it works

The platform only reports how many messages are unread; it never sends the messages themselves.
They are read on the account portal's messages page, which is the default target of the entry and
the same page for every type of user.

## Accessibility

The avatar has no visible label, so the widget relies on three texts, which must match the
page's language:

- `text-current-user` describes the avatar; `{user}` is replaced with the user's full name.
- `text-user-links` labels the user menu itself.
- The `text-access-user-links` slot is the accessible name of the button opening the user menu. It
  is translated by default.

The first two are properties, since they end up in attributes, which a slot cannot fill. The number
of unread messages is announced together with `text-unread-messages`, which is translated by
default.
